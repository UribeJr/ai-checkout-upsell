## 3. Core architecture decision

**Build a hybrid Product Intelligence + checkout decision engine.** The LLM is a recommender, NOT the authority over what can be sold or charged.

Three separate responsibilities:

1. **Shopify:** source of truth for products, variants, availability, price, checkout, and final order mutation.
2. **Our backend + database:** product ingestion, durable enrichment, candidate retrieval, business constraints, caching, logging and analytics.
3. **LLM:** interprets product relationships offline, then ranks a small eligible shortlist and drafts grounded offer messaging at decision time.

**Principle:** `AI recommends -> backend validates -> Shopify calculates/applies purchase changes`.

### A. Background product intelligence pipeline

```text
Initial catalog sync or product update webhook
  -> verify request and enqueue/dedupe job
  -> fetch fresh Shopify product + variant data
  -> calculate hash of AI-relevant fields
  -> if semantic fields changed, run AI product enrichment
  -> validate enrichment against source facts and schema
  -> persist ProductIntelligence and ProductRelationship
  -> refresh any affected recommendation cache entries
```

- Do not call the LLM directly inside a high-volume webhook handler.
- A price/stock-only change updates operational data/invalidation, not semantic enrichment.
- Deduplicate bursts of product updates; use idempotency and retries.
- Product enrichment should understand **use cases, format, compatibility and complementary value**, not simply keyword similarity.
- Never invent wellness, medical, efficacy, ingredient or safety claims. Customer copy must stay within merchant-verified product facts.
- For this case study, a manual initial sync and a simple refresh mechanism may be sufficient before full webhook/worker infrastructure. Document anything deferred.

### B. Customer post-purchase decision pipeline

> **Revised 2026-10-30 (developer):** no LLM call at checkout. The AI writes offer copy offline per relationship; checkout = stored candidates -> deterministic rules -> live Shopify check -> stored or template copy. See `docs/phase-2-plan.md`. The pipeline below is the original suggested design.


```text
Eligible Shopify checkout reaches post-purchase lifecycle
  -> authenticated extension/backend request with checkout reference/context
  -> derive compact purchased-line-item/order context
  -> retrieve complementary candidates from Product Intelligence DB
  -> aggregate matches for multi-item orders and dedupe
  -> apply deterministic eligibility filtering
  -> attempt fresh, context-appropriate cached decision
  -> otherwise ask LLM to rank 3-5 eligible candidates
  -> validate returned variant ID and customer-facing claims
  -> on timeout/invalid response, use deterministic fallback or no offer
  -> display one transparent, actionable post-purchase offer
  -> Shopify calculates and applies an authorized changeset if accepted
  -> record impression / acceptance / rejection / successful attributed revenue
```

**Important Shopify lifecycle caveat:** `Checkout::PostPurchase::ShouldRender` executes during the payment stage, before the customer has necessarily finished checkout. Do not assume the final Admin order is already available there. Use documented `inputData`, `initialPurchase.referenceId`, authenticated backend requests, and approved checkout lifecycle data. `Checkout::PostPurchase::Render` is the customer-facing post-payment stage. Follow the official tutorial for token handling, `calculateChangeset`, `applyChangeset`, signed changesets and `done` rather than inventing a generic order-update flow.

**Timing:** Keep checkout latency low. `ShouldRender` may preload the offer. Favor cached decisions and short bounded LLM timeouts; rendering must degrade safely. Ensure no offer is shown for an unsupported checkout/payment scenario. Do not assume Shop Pay shares storage between `ShouldRender` and `Render` (Shopify documents an exception).

### C. Product recommendation improvement over time

**MVP:** AI-informed enrichment + contextual shortlist ranking; log outcomes.

**Future:** incorporate observed performance (acceptance, incremental revenue per impression, contribution margin, confidence/sample size and order context) into ranking. Later use controlled experimentation or a contextual bandit to avoid prematurely overfitting to early winners.

**Do NOT claim the system already learns on its own.** Simply logging analytics does not improve future recommendations until feedback is explicitly incorporated. This is a deliberate future-phase design, not MVP scope.

## 4. AI input/output contracts

### A. Offline product enrichment

Input: product title, cleaned description, product type/tags, variant characteristics, approved facts/metafields, and a small known catalog context when needed. Do not send secrets or identifiable customer data.

Desired structured output (illustrative; adapt schema to actual catalog):

```json
{
  "category": "Nutrition",
  "format": "Single-serving packets",
  "useCases": ["travel", "portability"],
  "complementaryUseCases": ["daily greens routine"],
  "offerAngles": ["convenience"],
  "approvedFactReferences": ["packaging_format"],
  "relationshipSuggestions": [
    {
      "targetProductId": "example-product-id",
      "type": "complementary",
      "reason": "portable format complements a larger at-home package",
      "score": 0.88
    }

}
```

Enrichment data is a **hypothesis** until validated; don't present an LLM-inferred fact as a verified merchant claim. A relationship score is not a real probability of conversion.

### B. Runtime offer selection

Input (only already-eligible shortlist + compact order context):

```json
{
  "order": {
    "lineItems": [{ "productId": "p1", "title": "Daily Greens", "quantity": 1 }],
    "subtotal": 49.99,
    "currency": "USD"
  },
  "candidates": [
    {
      "variantId": "v-travel",
      "title": "Travel Packs",
      "price": 19.99,

      "verifiedFacts": ["single-serving packets"]
    },
    {

      "title": "Shaker Bottle",
      "price": 14.99,
      "relationship": "mixing accessory",
      "verifiedFacts": ["reusable mixing bottle"]
    }
  ]
}
```

Expected structured output:

```json
{
  "selectedVariantId": "v-travel",
  "offerAngle": "convenience",
  "headline": "Take Your Routine Anywhere",
  "description": "Add convenient single-serving travel packs to your order.",
  "reason": "Adds portability without duplicating the purchased item"
}
```

**Contract requirements:**

- Validate JSON schema server-side. The selected ID must match an approved candidate.
- Model must only choose from provided candidates; never invent SKUs, products, discounts, prices or claims.
- Recheck product and variant eligibility before signing/applying any purchase changes.
- Prices and discounts come from Shopify and deterministic business policy, not LLM output.
- Log `modelName`, prompt/schema version, fallback source, duration, and optional non-sensitive decision rationale for debugging and reporting.
- Build a provider adapter (`ai-provider.server.js` or similar) so the LLM vendor can be changed; don't hardcode a vendor yet unless the project owner chooses one.
- Use bounded retries/timeouts, a deterministic fallback, and no offer when nothing safe is eligible.

These are fictional example products and prices. Do not claim they are Gruns' actual products.

## 5. Candidate eligibility and ranking

**Deterministic filtering happens BEFORE LLM ranking:**

- Exclude exact purchased variants and clearly redundant duplicates where not an intentional upsell.
- Exclude inactive/unpublished/unavailable variants, invalid market/currency combinations and unsupported purchase types.
- Respect merchant price ceilings, discount constraints and any allowed/disallowed categories.
- Confirm any required shipping and checkout eligibility through documented Shopify capabilities.
- Prefer complementary use cases (e.g., a portable format or mixing accessory) over title/description resemblance alone.
- Handle multi-item orders by aggregating, deduping and ranking relationships without repeatedly recommending purchased items.
- Limit LLM input to a shortlist (e.g., 3-5 products) and persist the outcome/cache key with eligibility-sensitive invalidation.

**MVP ranking ideas:** relationship strength, distinct complementary value, relative offer price/basket value and purchase friction. AI then picks one of the valid candidates and explains its reasoning. Don't fabricate a trained conversion model or claim calibrated confidence scores.

## 6. Proposed data model (starting point, not an imposed schema)

Inspect existing Prisma models first and evolve them minimally.

- `ProductIntelligence`: shop ID, Shopify product ID, metadata snapshot/version, description hash, category, format, JSON use cases/attributes, verified fact references, enrichment status/version/timestamp.
- `ProductRelationship`: shop ID, source Shopify product ID, target Shopify product ID, relationship type, relevance score, explanation, enrichment version. Support many-to-many and re-enrichment.
- `OfferDecision`: shop ID, checkout/reference identifier, selected variant ID, purchased-product context (minimal), decision source (`cache`, `ai`, `fallback`), model/prompt/strategy versions, timestamp, policy/version, idempotency key.
- `OfferEvent`: decision ID, event type (`impression`, `accepted`, `declined`, `apply_failed` or similar), event timestamp, value/currency where appropriate, unique idempotency key.

Consider a small cache table or equivalent if necessary. Avoid premature schema bloat. Keep the existing session model and migrations intact.

**Reporting definitions:**

- Impression = offer was actually displayed, not merely preloaded in `ShouldRender`.
- Acceptance = buyer chose to accept; distinguish from a successful Shopify changeset application.
- Conversion rate = successful accepted offers / displayed offers (define clearly).
- Attributed incremental revenue = successfully applied post-purchase additions, not the original order's revenue. Store currency and explain how refunds/cancellations would be handled in production.
- Top-performing offers = rank by revenue per impression and show conversion alongside it; guard against tiny sample sizes.

Use an authenticated event API, idempotent event recording and minimal customer data.

## 11. Design principles to explain in the interview

1. **Why two AI stages?** Expensive catalog reasoning happens ahead of time; low-latency order-context ranking happens at checkout.
2. **Why an eligibility gate?** An LLM may recommend relevance but should never control catalog truth, discount policy or order mutation.
3. **Why decouple modules?** Independently test Shopify integration, product intelligence, offer decisions, and analytics.
4. **Why event-level measurement?** Impression -> acceptance -> successful application yields auditable conversion and incremental revenue metrics.
5. **How does it improve?** Recorded outcomes allow later performance-aware ranking, A/B experiments and sample-size safeguards; this is future work, not magic self-learning.
6. **Why keep scope small?** Prove an end-to-end revenue event with strong reliability before adding sophistication.
